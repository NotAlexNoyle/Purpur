## 0315 Save player data using a RocksDB database

| ID | Sev | Issue | Evidence | Impact | Fix |
|---|---|---|---|---|---|
| DB-1 | P0 | Conflicts with MyWorlds + BKCommonLib on the live server (`beta-2-plugins/MyWorlds/config.yml:15` `useWorldInventories: true`, main inventory group `world`; `PlayerFileDataHandler_1_16` in `BKCommonLib-1.19.4-v2.jar` replaces `PlayerList.playerIo` with a hooked copy that intercepts `load/save/getSeenPlayers`, and MyWorlds reads and writes `<world>/playerdata/<uuid>.dat` directly through its own `getPlayerDir()` template). The constructor runs `migrate()` before any plugin loads and renames that directory | line 259 (`Files.move` to `playerdatamigrated`) | First boot on live: every player's main-group inventory, ender chest, XP, and position appear empty. Recovery: stop, roll back to a build without this patch, delete the new `playerdata`, rename `playerdatamigrated` back, delete `playerdatadb`. Deleting `playerdatadb` alone is not enough: with this patch still installed the marker is gone, so the next boot migrates and renames again. Anything written to the new files since the upgrade is lost either way | Do not rename the source directory; make migration a no-op while the folder is in active use; decide whether RocksDB storage is meaningful at all with MyWorlds owning player files |
| DB-2 | P1 | With MyWorlds hooked, RocksDB is a stale snapshot. Online-player saves go through `PlayerList.playerIo` (`PlayerList.java:154,561`), which BKCommonLib replaces, and never reach `saveCompoundTag`; `CraftOfflinePlayer` and `CraftServer.getOfflinePlayers` read the unhooked `console.playerDataStorage` (`CraftOfflinePlayer.java:41`, `CraftServer.java:2127`). `Utilities-OG` ≥ 1.7.4 `PlayerDataUtils.java:15-24` reflects `getPlayerData(UUID)`/`saveCompoundTag` off `playerIo` for the same reason, and looks them up with `getDeclaredMethod` on `playerIo.getClass()`, which is BKCommonLib's generated subclass once MyWorlds has hooked it (mountiplex only declares the intercepted `load/save/getSeenPlayers` there) | lines 297-306 (`save`), 391-401 (`getPlayerData`), 464-467 and 549-561 (`CraftOfflinePlayer`), 581-589 (`getOfflinePlayers`) | `hasPlayedBefore()` false for everyone who first joined after the upgrade; `getLastPlayed/getLastSeen` frozen at migration time for offline players (online players still answer from the live entity); Purpur's offline `setLocation`/`teleportOffline` write a record nothing reads. The next DiamondBank-OG (`84ed433`; the deployed `1619554` jar has no offline path and the deployed Utilities-OG 1.7.3 has no `PlayerDataUtils`) takes offline inventories through `InventorySnapshot.from/restoreTo` (`InventorySnapshot.kt:48,52,79` → `UtilitiesOG.getInventoryData/getHeldItemSlot/setInventoryData`). Enable order decides the failure: if Utilities-OG enables before MyWorlds it keeps the original storage object, so an offline `consumeFromPlayer`/`playerPayPlayer` charges the bank part and removes the remainder from the migration-time inventory nobody loads, the player keeps those items and the call reports success; if MyWorlds hooks first, `PlayerDataUtils.java:23-24` finds no methods, logs "Not running TrueOG Purpur jar", and every offline call throws `UnsupportedOperationException` out of `runOnMainThread` (`MainThreadBlock.kt:21-22`) instead of returning a failure | There is no routing fix inside the server: BKCommonLib's hook overrides `load/save/getSeenPlayers` only, so pointing `CraftOfflinePlayer` at `playerIo` would still call the unhooked `getPlayerData`. Mainline works because `CraftOfflinePlayer`, OpenInv, and MyWorlds read the same `.dat` file. Either keep `.dat` files as the source of truth for offline reads, or drop the patch |
| DB-3 | P1 | Migration is all-or-nothing and aborts server start. Every `*.dat` regular file goes through `UUID.fromString` and `readCompressed`; any `IllegalArgumentException` or `IOException` sets `success=false` and throws. Vanilla's own save path leaves `<uuid>-<random>.dat` temp files behind on a crash mid-save, and they match the `endsWith(".dat")` filter | lines 240-256 | One leftover temp file or one corrupt file → "Failed to start the minecraft server" on every boot until an operator deletes it. Vanilla only failed for that one player. "All-or-nothing" is about startup, not the data: records migrated before the bad file are already in the DB when the constructor throws, and the marker is not, so the next boot re-migrates them | Skip and log unparsable files; write the marker only after the survivors are migrated |
| DB-4 | P2 | No `.dat_old` backups and no export back to `.dat`. `load()` catches any `Exception` from `get()` (including a transient `RocksDBException`) and continues with a null tag, so the player loads fresh and the next save overwrites the record. The catch-and-continue is inherited from vanilla and logs a WARN; what is new is that the overwritten previous value no longer exists anywhere | line 275 (bare `put`), 361-363 (`load` swallow) | Downgrade to mainline cannot see any change since migration (the DB itself is untouched); a transient DB read error followed by one save replaces the record with a fresh player, with one WARN line as the only trace | Keep a previous-value copy per key, or an export command |
| DB-5 | P3 | Marker written before the rename. If `playerdatamigrated` already exists (operator restored `playerdata` and deleted the DB), `Files.move` throws after the marker persisted, so the next boot skips migration | lines 258-259 | The records were copied before the marker, so nothing is missing on the next boot; the server fails to start once (`Could not successfully migrate player data`), then starts with the directory still in place and silently ignores it from then on, so any later edits or restores into `playerdata` never reach the DB | Rename first, then write the marker; or use a timestamped target |
| DB-6 | P3 | `saveCompoundTag`/`saveCompoundTagCustom` after `close()` return silently, no log. | DB-7 | P3 | `close()` sets a volatile flag then frees native handles; a `get`/`put`/`createColumnFamily` that passed the flag check on another thread dereferences a freed handle. Off-main callers exist (`AsyncPlayerPreLoginEvent` handlers calling `hasPlayedBefore()`, async scheduler tasks). BKCommonLib's hook copies fields into a second instance whose `closed` flag is never set, since `close()` runs on `MinecraftServer.playerDataStorage`, not on the hooked `PlayerList.playerIo` | lines 171-188, 191-196, 268-275, 309-311 | SIGSEGV / `hs_err` at shutdown in the narrow window after the network stops; the 5 s worker wait in `disablePlugins` narrows it but does not close it. Kept at P3 because a live occurrence has not been shown | Read-write lock around native calls, or `close()` after all plugin threads are joined |
| DB-8 | P3 | `CraftOfflinePlayer` first/last-played/login/seen return 0 instead of the file's mtime when the NBT key is absent; the `load()` block that seeded `firstPlayed` from mtime is also gone. Kept at P3 because no such record is known on the live server (every migrated `.dat` was written by CraftBukkit's save and carries the keys) | Return `-1` or the migration timestamp instead of 0 |
| DB-9 | P3 | Reads create column families. `getPlayerDataCustom` goes through `getOrCreateWorldColumnFamily` (line 412), so a lookup for a world name that has no data creates a persistent `world:<name>` column family on disk. No live plugin calls the per-world API yet | Look up without creating on the read path; add a way to drop a world's column family |
| DB-10 | **P1** | **OpenInv offline-inventory saves throw `NoSuchMethodError`.** The patch deletes `PlayerDataStorage.getPlayerDir()` (lines 442-444).
